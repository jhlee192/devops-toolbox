파일 일괄 수정 (ls / grep / sed)

숫자가 섞인 경로를 숫자 순으로 나열

ls -lv <files>
  • 언제번호 붙은 파일·디렉터리를 1, 2, 3 순서로 보고 싶을 때
  • 주의<files>에는 data*/conf/app.yml처럼 *를 넣어 여러 파일을 한 번에 지정한다. *는 "아무 글자나 몇 개든"이라는 뜻이고, 셸이 실행 전에 맞는 파일 이름들로 바꿔 넣는다
  • 주의셸이 *를 펼칠 때와 기본 ls는 글자 단위 사전순으로 정렬한다. 그래서 첫 글자 1이 2보다 작다고 보고 10이 2보다 앞에 온다. -v를 주면 10을 숫자 10으로 읽어서 2 < 3 < ... < 10 순서가 된다
  • 주의-v는 리눅스 ls에만 있다. macOS 기본 ls엔 없다

여러 파일을 숫자 순으로 grep

ls -v <files> | xargs grep -H <keyword>
  • 언제여러 파일을 순서대로 grep할 때. 수정 전후 확인용
  • 주의grep <keyword> data*/...처럼 바로 쓰면 셸이 *를 사전순으로 펼쳐서 순서가 꼬인다. ls -v로 파일 목록을 먼저 정렬하고, xargs가 그 목록을 grep 뒤에 붙여서 실행한다
  • 주의-H가 있어야 줄 앞에 파일명이 붙는다
  • 연관grep ... | sort -V로 결과를 정렬해도 되지만, 한 파일에서 여러 줄 걸리면 파일 안의 줄 순서까지 섞인다
  • 연관다음 줄까지 보려면 -A1. 찾을 문자열이 -로 시작하면 옵션으로 오해하니 앞에 --를 붙인다

치환 결과 미리보기

sed -n 's/<pattern>//p' <files>
  • 언제sed -i로 고치기 전에 바뀔 줄만 확인할 때
  • 주의-n은 sed가 모든 줄을 출력하는 걸 끄고, 끝의 p는 바뀐 줄만 출력한다. 파일은 바뀌지 않는다

여러 파일에서 문자열 일괄 삭제

sudo sed -i.bak 's/<pattern>//' <files>
  • 언제여러 파일에서 같은 문자열을 한 번에 지울 때
  • 주의s/찾을것/바꿀것/에서 바꿀 것을 비워 두면 삭제가 된다
  • 주의<pattern> 안의 *는 파일 지정할 때의 *와 뜻이 다르다. 여기선 "바로 앞 글자가 0번 이상 반복"이다. [0-9]*는 "숫자가 몇 개든"
  • 주의sed에서 |는 특별한 의미가 없는 그냥 글자라 앞에 \를 붙이지 않고 그대로 쓴다
  • 주의-i.bak은 파일을 직접 고치고 원본을 .bak으로 남긴다. 실행할 때마다 .bak이 덮어써지니, 맨 처음 원본이 필요하면 첫 .bak을 다른 이름으로 옮겨둔다
  • 주의root로 sed -i를 실행해도 원래 파일의 소유자와 권한은 그대로 유지된다
  • 연관쉼표로 나열된 목록에서 항목 하나 지우기 — s/, <word>\b//. 앞 쉼표까지 지워야 목록이 깔끔하다. \b는 "단어가 여기서 끝남"이라는 뜻이라 <word>2처럼 이름이 비슷한 항목은 안 걸린다. 목록 맨 앞 항목은 <word>, 형태라 이 패턴에 안 걸린다

특정 줄과 다음 줄을 함께 삭제

sudo sed -i.bak '/<first_line>$/{N;/<next_keyword>/d}' <files>
  • 언제YAML 리스트 항목처럼 두 줄짜리 블록을 빼낼 때
  • 주의<first_line>에 맞는 줄을 찾으면 N이 다음 줄을 읽어 붙인다. 붙인 두 줄에 <next_keyword>가 있을 때만 d로 둘 다 지운다. 다음 줄이 예상과 다르면 지우지 않는다
  • 주의$는 "줄 끝"이라는 뜻이다. 붙여야 crawler2처럼 뒤에 글자가 더 있는 줄이 안 걸린다
  • 연관미리보기는 -i 없이 돌려서 원본과 비교 — sed '<script>' <file> | diff <file> - (-는 앞 명령의 출력을 받는다는 뜻)

sed 백업 파일 일괄 삭제

sudo rm -f <files>.bak
  • 언제sed -i.bak 결과를 확인한 뒤 백업을 정리할 때
  • 주의먼저 ls -lv <files>.bak로 목록을 확인한다
  • 연관위치가 흩어져 있으면 find <dir> -name '<name>.bak' -print로 확인한 뒤 -print를 -delete로 바꿔 지운다

체크섬

공개된 SHA256 값으로 파일 검증

echo "<sha256>  <file>" | sha256sum -c -
  • 언제다운로드한 파일(JDK 압축 파일, 설치 파일 등)이 배포처가 공개한 SHA256 값과 같은지 확인할 때. 체크섬 파일 없이 해시 문자열만 받은 경우에 쓴다
  • 주의SHA256은 파일 내용으로 계산한 64자리 값이다. 1바이트만 달라도 값이 완전히 바뀌므로, 값이 같으면 받는 도중 깨지거나 바뀌지 않았다고 볼 수 있다
  • 주의-c는 입력을 해시 파일명 목록으로 읽고, 그 파일을 다시 계산해 비교한다. 끝의 -는 목록을 파일 대신 표준입력에서 읽으라는 뜻이다. 결과는 <file>: OK 또는 FAILED로 나온다
  • 주의해시와 파일명 사이는 공백 2칸이 표준 형식이고, 반드시 한 따옴표 안에 넣는다. echo "<sha256>" <file>처럼 따옴표 밖에 파일명을 두면 공백이 1칸이 된다. GNU coreutils는 1칸도 받아주지만 Alpine 같은 busybox 환경에서는 형식 오류가 날 수 있다
  • 주의<file>은 현재 디렉터리 기준 경로다. 파일이 있는 디렉터리에서 실행한다
  • 주의macOS에 sha256sum이 없으면 shasum -a 256 -c -로 바꾼다. -a 256을 빼면 SHA-1로 계산된다
  • 주의체크섬은 파일 손상만 잡는다. 해시값과 파일을 같은 곳에서 받았다면 둘 다 바꿔치기된 경우는 잡지 못한다

DNS (노드)

노드가 실제로 쓰는 DNS 서버 확인

ls -l /etc/resolv.conf; cat /etc/resolv.conf
  • 언제노드나 Pod에서 DNS가 안 될 때 가장 먼저. nameserver와 search 도메인을 확인한다
  • 주의ls -l로 심볼릭 링크인지, 언제 다시 생성됐는지(수정 시각) 같이 본다. 첫 줄 주석(# Generated by NetworkManager)으로 누가 관리하는 파일인지 알 수 있고, 직접 고쳐도 그 서비스가 덮어쓴다
  • 주의search 줄에 IP 주소가 있으면 설정 실수다. 보통 보조 DNS를 search 도메인 칸에 잘못 넣은 경우다. 이러면 nameserver가 하나뿐이라 예비 서버가 없고, 모든 이름 뒤에 그 IP를 붙인 쓸모없는 질의가 나간다
  • 주의Kubernetes에서는 노드의 search 도메인이 Pod의 resolv.conf에도 그대로 붙는다
  • 연관NetworkManager 쪽 원래 설정은 nmcli -g ipv4.dns,ipv4.dns-search con show <connection>

NetworkManager 연결의 DNS 설정 확인

nmcli -t -f NAME,DEVICE con show --active
nmcli -g ipv4.method,ipv4.dns,ipv4.dns-search,ipv4.ignore-auto-dns con show <connection>
  • 언제resolv.conf가 왜 그렇게 생성됐는지 원래 설정을 볼 때
  • 주의-t는 콜론으로 구분한 짧은 출력, -f는 보여줄 열을 고른다. -g는 지정한 값만 줄마다 하나씩 뽑는다
  • 주의ipv4.dns는 nameserver, ipv4.dns-search는 search 도메인이다. ignore-auto-dns가 no면 DHCP로 받은 DNS도 섞인다
  • 연관RHEL 8 이하에서는 같은 내용이 /etc/sysconfig/network-scripts/ifcfg-<device>의 DNS1, DNS2, DOMAIN에 있다. grep -H -iE 'DNS|DOMAIN' /etc/sysconfig/network-scripts/ifcfg-*

특정 목적지로 가는 경로 확인

ip route get <ip>
  • 언제업스트림 DNS나 외부 서버로 패킷이 어느 인터페이스, 어느 게이트웨이로 나가는지 볼 때
  • 주의실제 패킷을 보내지 않고 라우팅 테이블에서 고른 결과만 보여준다. src가 이 경로로 나갈 때 쓰는 출발지 IP다

dig 없이 DNS 응답률 측정

python3 - <<'PY'
import socket, struct, random, time
server, name, n = "<dns-server>", "<name>", 120
ok = fail = 0; lat = []
for i in range(n):
    q = struct.pack(">HHHHHH", random.randint(0, 65535), 0x0100, 1, 0, 0, 0) \
        + b"".join(bytes([len(p)]) + p.encode() for p in name.split(".")) + b"\0" + struct.pack(">HH", 1, 1)
    s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); s.settimeout(2); t = time.time()
    s.sendto(q, (server, 53))
    try:
        d, _ = s.recvfrom(4096); ok += 1; lat.append(time.time() - t)
    except Exception:
        fail += 1; print("timeout", time.strftime("%H:%M:%S"))
    s.close(); time.sleep(0.4)
lat.sort(); print("ok=%d fail=%d p50=%.0fms max=%.0fms" % (ok, fail, lat[len(lat)//2]*1000, lat[-1]*1000))
PY
  • 언제노드에 dig, nslookup이 없을 때(bind-utils 미설치) DNS 서버가 응답하는지, 간헐적으로 응답을 놓치는지 측정할 때
  • 주의표준 라이브러리만 쓰는 UDP DNS 질의(A 레코드)다. 응답이 오기만 하면 성공으로 센다. NXDOMAIN도 응답이 온 것이므로 성공이다
  • 주의한 번 질의해서 성공하는 것과 계속 성공하는 것은 다르다. 간헐 장애는 여러 번 반복해야 보인다. n과 sleep 간격을 조절한다
  • 주의settimeout(2)보다 늦은 응답은 실패로 센다

resolv.conf 변경 이력 보기

sudo journalctl -u NetworkManager --since '<since>' --until '<until>' --no-pager | grep -iE 'dns|dhcp|resolv'
  • 언제resolv.conf가 언제, 무엇 때문에 다시 생성됐는지 따라갈 때

Docker

컨테이너 로그 설정 확인

sudo docker inspect <container> --format '{{.HostConfig.LogConfig}}'
  • 언제컨테이너 로그가 로테이션되고 있는지 볼 때
  • 주의{json-file map[]}처럼 map[]이 비어 있으면 로테이션 설정이 없는 것이다. 이 경우 로그가 끝없이 커진다

컨테이너 로그 파일 크기 확인

sudo sh -c 'ls -lh $(docker inspect <container> --format {{.LogPath}})'
  • 언제docker logs가 느리거나, /var/lib/docker가 커졌거나, dockerd CPU가 높을 때
  • 주의.LogPath는 그 컨테이너의 stdout 로그 파일 경로다. 보통 /var/lib/docker/containers/<id>/<id>-json.log
  • 주의이 경로는 root만 읽을 수 있다. 그래서 $(...) 치환까지 root 권한으로 돌도록 sudo sh -c '...'로 감싼다

컨테이너 환경변수 확인

sudo docker inspect <container> --format '{{range .Config.Env}}{{println .}}{{end}}'
  • 언제compose 파일을 찾지 않고, 실행 중인 컨테이너에 실제로 들어간 환경변수를 볼 때 (예: GitLab의 GITLAB_OMNIBUS_CONFIG)
  • 주의range ... println은 변수 하나를 한 줄로 출력한다. 여러 줄짜리 값은 그대로 여러 줄로 나온다
  • 주의비밀번호나 키가 그대로 출력된다. 공유할 때는 가린다

daemon.json 문법 검사

sudo python3 -m json.tool /etc/docker/daemon.json
  • 언제daemon.json을 고친 뒤 dockerd를 재시작하기 전에
  • 주의문법이 틀린 채로 재시작하면 dockerd가 아예 뜨지 않는다. 그러면 모든 컨테이너가 내려간 상태가 된다
  • 주의json.tool은 JSON을 읽어서 다시 예쁘게 출력한다. 오류가 있으면 줄 번호와 함께 실패한다. 파일은 바뀌지 않는다

sudo systemctl restart docker
  • 언제daemon.json(로그 기본값 등)을 바꾼 뒤
  • 주의live-restore가 꺼져 있으면 서버의 모든 컨테이너가 같이 재시작된다
  • 주의restart: always여도 사용자가 직접 docker stop한 컨테이너는 자동으로 다시 뜨지 않는다
  • 주의로그 기본값(log-driver, log-opts)은 이후에 새로 만드는 컨테이너에만 적용된다. 기존 컨테이너는 아래처럼 다시 만들어야 한다

compose 컨테이너 재생성

cd <compose-dir> && sudo docker compose down && sudo docker compose up -d
  • 언제환경변수나 로그 설정처럼 컨테이너를 만들 때 고정되는 값을 바꾼 뒤
  • 주의down은 컨테이너와 네트워크를 삭제한다. 볼륨에 둔 데이터는 남는다. 컨테이너 stdout 로그 파일은 같이 삭제된다
  • 주의volumes가 $VAR/path 같은 변수 형태면 sudo가 환경변수를 넘기지 않아 빈 경로가 될 수 있다. 재생성 전에 sudo docker compose config로 실제로 풀린 경로를 확인한다. compose는 같은 디렉터리의 .env를 자동으로 읽는다

GitLab (Omnibus / Docker)

서비스 구성요소 상태 확인

sudo docker exec <container> gitlab-ctl status
  • 언제GitLab 안의 puma, sidekiq, gitaly, postgresql 같은 구성요소가 모두 떠 있는지, 언제 재시작됐는지 볼 때
  • 주의줄마다 run: <서비스>: (pid N) <초>s 형태로 나온다. 끝의 숫자는 그 서비스가 떠 있은 시간(초)이다. 한 서비스만 유독 작으면 최근에 죽었다가 다시 뜬 것이다
  • 주의Docker가 아니라 서버에 직접 설치했다면 sudo docker exec <container>를 빼고 sudo gitlab-ctl status로 실행한다. 이 파일의 다른 명령도 같다

  • 주의설정 도구(Chef)를 실제로 적용하지 않고 계산만 해서 JSON으로 출력한다. 출력 끝의 Converging 0 resources는 아무것도 바꾸지 않았다는 뜻이다. 실행에 10초 정도 걸린다
  • 주의사용자가 지정한 값과 일부 계산된 값만 나온다. 기본값은 대부분 빠지므로, 출력에 없다고 해서 꺼져 있다는 뜻은 아니다
  • 주의출력에 비밀번호나 시크릿이 섞일 수 있다. 통째로 공유하지 않는다
  • 주의출력 앞뒤에 JSON이 아닌 로그 줄이 붙는다. 그대로 JSON 파서에 넣으면 Extra data 에러가 난다
  • 연관Rails가 실행될 때 채우는 기본값은 여기서 안 보인다. 아래 "Rails 설정 값 직접 조회"로 확인한다

sudo docker exec <container> grep -n "<key>" /opt/gitlab/embedded/service/gitlab-rails/config/initializers/1_settings.rb

sudo docker exec <container> gitlab-rails runner 'puts Gitlab.config.gitlab.email_enabled; puts ActionMailer::Base.delivery_method'
  • 언제메일이 실제로 켜져 있는지, 어떤 방식(smtp/sendmail)으로 나가는지처럼 최종 적용 값을 확인할 때

  • 주의GitLab이 쓰는 인증 라이브러리(Devise)의 설정값이다. 따로 바꾸지 않았다면 10과 10 minutes가 나온다

  • 주의-c를 빼면 /opt/gitlab/embedded/conf/nginx.conf를 검사하고 syntax is ok가 나온다. 이 파일은 패키지 기본 설정이라 실제로는 쓰이지 않는다. 출력에 /var/opt/gitlab/nginx/conf/nginx.conf가 나와야 제대로 검사한 것이다

  • 주의hup은 Nginx에 HUP 신호를 보내 설정만 다시 읽게 한다. nginx -s reload와 같다. gitlab-ctl restart nginx는 진행 중인 연결이 끊긴다

  • 주의-c는 일치하는 줄 수를 센다. 0이면 설정이 사라진 것이므로 다시 넣는다
  • 주의/var/opt/gitlab/nginx/conf/ 아래 파일은 reconfigure·업그레이드 때 다시 생성된다. 영구적으로 넣으려면 gitlab.rb의 registry_nginx['custom_gitlab_server_config'] 같은 설정을 쓴다

Java 인증서 (keytool)

truststore에서 CA 이름으로 검색

keytool -list -v -cacerts -storepass changeit | grep -i 'Owner:' | grep -i '<ca-name>'
  • 언제Java가 HTTPS 호출에서 PKIX path building failed를 낼 때, 그 서버 인증서의 루트 CA가 JVM의 신뢰 저장소(cacerts)에 들어 있는지 볼 때
  • 주의cacerts에는 서버 인증서가 아니라 루트 CA가 들어 있다. 루트 CA만 있으면 그 CA가 발급한 서버 인증서는 따로 등록하지 않아도 통과한다. 루트 CA 이름은 openssl s_client ... -showcerts 출력의 마지막 i:(발급자)에서 확인한다
  • 주의-cacerts는 실행한 그 JDK의 기본 cacerts를 가리킨다(Java 9 이상). Java 8은 -keystore $JAVA_HOME/jre/lib/security/cacerts로 지정한다. 앱이 쓰는 JDK와 다른 keytool로 보면 엉뚱한 파일을 보게 된다
  • 주의-v(상세 출력)를 붙여야 Owner:(인증서 주인, subject) 줄이 나온다. changeit은 cacerts의 기본 비밀번호다
  • 주의앱이 -Djavax.net.ssl.trustStore=<path>로 별도 파일을 쓰고 있으면 기본 cacerts는 무시된다. ps -ef | grep java로 이 옵션이 붙어 있는지 먼저 본다
  • 연관없으면 아래 "루트 CA 인증서 등록"

CA 이름으로 alias 찾기

keytool -list -v -keystore <keystore> -storepass changeit | grep -iE 'Alias name|Owner:' | grep -iB1 '<ca-name>'
  • 언제등록된 인증서를 지우거나 확인하려는데 저장소 안에서 부르는 이름(alias)을 모를 때
  • 주의grep -B1은 걸린 줄 바로 위 1줄도 같이 보여준다. 출력에서 Alias name이 Owner 바로 위에 오므로 alias가 함께 나온다
  • 연관찾은 alias로 "특정 alias 등록 여부 확인", "인증서 삭제"

특정 alias 등록 여부 확인

keytool -list -cacerts -storepass changeit -alias <alias>
  • 언제인증서를 등록한 뒤 제대로 들어갔는지 볼 때
  • 주의없으면 Alias <alias> does not exist 에러로 끝난다

루트 CA 인증서 등록

keytool -importcert -cacerts -storepass changeit -alias <alias> -file <cert-file> -noprompt
  • 언제사설 CA나 JDK 기본 cacerts에 없는 CA(정부 GPKI 등)가 발급한 인증서를 Java가 신뢰하게 만들 때
  • 주의옵션 — -importcert 인증서 추가 / -alias 저장소 안에서 부를 이름(기존 것과 겹치면 실패) / -file 등록할 인증서(PEM, DER 둘 다 됨) / -noprompt "신뢰하시겠습니까?" 확인 생략
  • 주의보통 루트 CA만 넣는다. 중간 인증서는 서버가 보내는 게 정상이다. 서버가 중간 인증서를 안 보내면 루트를 넣어도 PKIX 에러가 계속 난다. 이때는 서버에 fullchain을 등록하는 게 근본 해결이고, 서버를 못 고칠 때만 중간 CA도 같이 넣는다
  • 주의서버 인증서 자체를 넣는 건 피한다. 인증서를 갱신할 때마다 다시 넣어야 하고, 놓치면 그날부터 PKIX 에러가 난다. 자체 서명 인증서는 자기가 곧 루트라서 예외다
  • 주의루트 인증서는 CA 공식 배포처에서 받는다. 접속 대상 서버가 보내준 것을 그대로 쓰면 신뢰의 출발점을 상대에게서 받는 셈이다
  • 주의등록한 뒤 Java 프로세스를 재시작해야 반영된다. truststore는 JVM이 뜰 때 읽는다
  • 주의JDK를 업그레이드하거나 재설치하면 cacerts가 새 파일로 바뀌어 등록한 CA가 사라진다. 배포 스크립트나 Dockerfile에 등록 단계를 넣어 둔다
  • 연관"특정 alias 등록 여부 확인"

인증서 삭제

keytool -delete -alias <alias> -keystore <keystore> -storepass changeit
  • 언제잘못 넣은 인증서를 뺄 때. 또는 cacerts 복사본에서 특정 CA를 빼고 -Djavax.net.ssl.trustStore=<복사본>으로 실행해 "이 CA가 없으면 PKIX 에러가 나는지" 재현할 때
  • 주의원본 cacerts에서 공인 루트 CA를 지우면 그 CA를 쓰는 외부 호출이 전부 PKIX로 실패한다. 재현할 때는 cp로 복사본을 만들어 거기서 지운다

컨테이너 안 JVM에 호스트 인증서 등록

docker exec -i <container> keytool -importcert -cacerts -storepass changeit -alias <alias> -noprompt < <cert-file>
  • 언제인증서 파일은 호스트에 있는데 컨테이너 안의 Java에 등록할 때
  • 주의docker exec로 실행한 명령은 컨테이너 안에서 돈다. 그래서 -file <cert-file>로 주면 호스트 파일을 못 찾는다. -file을 빼면 keytool이 표준입력에서 인증서를 읽으므로, 호스트 쉘의 < 리다이렉트로 내용을 넘긴다
  • 주의-it가 아니라 -i만 쓴다. -i는 표준입력을 컨테이너로 연결하고, -t는 터미널을 붙인다. 입력을 파일로 넘기면서 -t를 붙이면 the input device is not a TTY로 실패한다
  • 주의docker restart로는 유지되지만, 컨테이너를 지우고 다시 만들면(docker rm, compose 재생성, 이미지 업데이트) 사라진다. 계속 쓸 거면 Dockerfile에 COPY + RUN keytool -importcert ...로 넣는다
  • 연관파일을 먼저 넣고 싶으면 docker cp <cert-file> <container>:/tmp/ 후 -file /tmp/<cert-file>로 등록. 등록 뒤 docker restart <container>

  • 주의로그 형식은 read udp <coredns-pod-ip>:<port>-><upstream-ip>:53: i/o timeout이다. 질의 이름과 레코드 타입(A/AAAA), 어느 업스트림인지가 같이 찍힌다
  • 주의기동 직후 <숫자>.<숫자>. HINFO 질의가 timeout이면 loop 플러그인의 자가 점검 질의다. 이것까지 실패하면 업스트림 전체가 안 닿는 상태다

CoreDNS 설정(Corefile) 확인

  • 주의--rm -i --restart=Never는 명령이 끝나면 Pod를 지우는 일회성 실행이다. -i가 없으면 출력을 못 받는다

  • 주의손으로 하는 질의는 이름 하나만 물어본다. 실제 앱은 search 도메인을 붙인 이름과 AAAA까지 여러 번 묻기 때문에, 이게 성공해도 앱 쪽 질의는 실패할 수 있다

Linux 프로세스·커널

D state로 멈춘 프로세스 찾기

for f in /proc/[0-9]*/stat; do
  s=$(timeout 1 cat $f 2>/dev/null) || continue
  set -- $s; [ "$3" = D ] && echo "$1 $2 D"
done
  • 언제ps, top, pgrep, kubectl exec가 응답 없이 멈출 때. 커널 안에서 대기하다 깨어나지 못한 프로세스가 있는지 찾는다
  • 주의D state(uninterruptible sleep)는 I/O나 커널 락을 기다리는 상태라 kill -9로도 죽지 않는다. 기다리는 대상이 끝내 안 풀리면 재부팅해야 정리된다
  • 주의ps가 멈추는 이유는 이런 프로세스의 /proc/<pid>/cmdline을 읽으려다 같은 메모리 락에 걸리기 때문이다. /proc/<pid>/stat은 그 락 없이 읽혀서 이 방법은 멈추지 않는다. timeout 1은 혹시 걸려도 1초 뒤 넘어가게 하는 안전장치다
  • 주의stat의 2번째 칸이 (프로세스명), 3번째 칸이 상태 문자다. 프로세스명에 공백이 있으면 칸이 밀린다
  • 연관어디서 멈췄는지는 sudo cat /proc/<pid>/stack

프로세스가 커널 어디서 멈췄는지 보기

sudo cat /proc/<pid>/stack
cat /proc/<pid>/wchan; echo
awk '/^(State|VmRSS|Threads)/' /proc/<pid>/status
  • 언제D state 프로세스가 무엇을 기다리는지 가릴 때. 디스크·NFS I/O인지, 메모리 관리 쪽 락인지
  • 주의stack은 root 권한이 필요하다. 맨 위 함수가 대기 지점이다. 스택의 함수 이름으로 커널 버그 리포트를 검색할 수 있다
  • 주의wchan이 0이어도 stack에는 내용이 나올 수 있다
  • 주의스택에 nfs_, rpc_가 있으면 NFS 서버 응답 대기, migration_entry_wait나 collapse_huge_page는 메모리 페이지 이동이나 THP(huge page 자동 병합) 쪽 대기다

프로세스 시작 시각 확인

sudo ls -ld --time-style=+%F_%T /proc/<pid>
  • 언제ps가 멈춰서 쓸 수 없을 때, 멈춘 프로세스가 언제부터 떠 있었는지 볼 때
  • 주의/proc/<pid> 디렉터리의 시각은 프로세스가 만들어진 시각으로 쓸 수 있다. --time-style=+%F_%T는 2026-01-01_12:00:00 형식으로 보여준다

THP(Transparent Huge Page) 설정 확인

cat /sys/kernel/mm/transparent_hugepage/enabled /sys/kernel/mm/transparent_hugepage/defrag
  • 언제Redis·DB 같은 메모리 집약 프로세스가 지연되거나, khugepaged가 D state일 때
  • 주의대괄호로 감싼 값이 현재 설정이다. [always]면 커널이 4KB 페이지를 2MB 단위로 자동 병합한다. 병합하려고 페이지를 옮기는 동안 그 메모리를 쓰는 프로세스가 기다린다
  • 주의Redis는 공식 문서에서 THP를 끄라고 권장한다

커널 메시지에서 hung task·OOM 찾기

sudo dmesg -T | grep -iE 'hung_task|blocked for more|oom|<pattern>' | tail -20
  • 언제프로세스가 멈췄거나 죽었을 때 커널이 남긴 경고를 볼 때
  • 주의-T는 사람이 읽는 시각으로 바꿔 보여준다. 다만 서스펜드 등이 있었으면 시각이 어긋날 수 있다
  • 주의결과가 비어 있어도 문제가 없다는 뜻은 아니다. hung task 경고는 kernel.hung_task_timeout_secs(기본 120초)를 넘겨야 찍히고, 링 버퍼가 차면 오래된 메시지는 사라진다

conntrack 테이블 사용량 확인

sudo cat /proc/sys/net/netfilter/nf_conntrack_count /proc/sys/net/netfilter/nf_conntrack_max
  • 언제UDP(DNS 등) 패킷이 간헐적으로 사라질 때 연결 추적 테이블이 꽉 찼는지 볼 때
  • 주의첫 줄이 현재 개수, 둘째 줄이 최대값이다. 최대값에 가까우면 새 연결이 버려지고 dmesg에 nf_conntrack: table full이 찍힌다

Loki

로그 보존 기간(retention) 설정 확인

cat /etc/loki/loki.yaml | grep retention
  • 언제Loki 로그가 언제 지워지는지, 아니면 무제한으로 쌓이는지 확인할 때
  • 주의Loki 파드 안에서 실행한다(kubectl exec). 설정 파일 경로는 설치 방식에 따라 다르다. 컨테이너 실행 인자의 -config.file= 값을 보면 알 수 있다
  • 주의retention_deletes_enabled: false와 retention_period: 0s가 나오면 삭제가 꺼져 있고 보존 기간도 무제한이다. 이 두 항목은 예전 방식인 table_manager의 설정이다
  • 주의파일에 적히지 않은 항목은 기본값으로 동작한다. compactor 방식의 retention_enabled는 grep에 안 나와도 기본값 false로 꺼져 있다

Nginx

적용 중인 설정 전체 보기

sudo nginx -T -c <nginx-conf> 2>/dev/null | grep -nE 'listen|server_name|location|limit_except|allow|deny|proxy_pass'
  • 언제어느 포트·도메인의 server 블록에 어떤 location이 있고 어디로 프록시되는지, 넣은 접근 제어가 실제로 들어갔는지 볼 때
  • 주의대문자 -T는 문법 검사 후 include된 파일까지 합친 전체 설정을 출력한다. 소문자 -t는 검사 결과만 보여 준다
  • 주의-c는 메인 설정 파일을 지정한다. 빼면 빌드 때 정해진 기본 경로를 읽는데, 그 파일이 실제로 쓰이는 설정이 아닐 수 있다
  • 주의2>/dev/null은 검사 결과 메시지(stderr)를 숨기고 설정 내용만 grep으로 넘긴다. -n은 줄 번호를 붙인다
  • 연관GitLab 번들 Nginx는 바이너리와 설정 경로가 다르다. [gitlab](gitlab.md#번들-nginx-설정-문법-검사) 참고

설정 문법 검사

sudo nginx -t -c <nginx-conf>
  • 언제설정을 고친 뒤 반영하기 전에 항상
  • 주의출력 첫 줄에 나온 경로가 실제로 쓰는 설정 파일인지 확인한다. -c 없이 실행하면 쓰이지 않는 기본 파일을 검사하고도 syntax is ok가 나올 수 있다
  • 주의include한 파일을 못 읽으면 open() "<경로>" failed (2: No such file or directory) 또는 (13: Permission denied)가 나온다. SELinux가 켜진 서버에서는 경로가 맞아도 13이 나올 수 있다

설정 무중단 반영

sudo nginx -s reload
  • 언제설정을 바꾸고 연결을 끊지 않고 반영할 때
  • 주의-s reload는 마스터 프로세스에 설정을 다시 읽으라는 신호를 보낸다. 기존 연결은 마무리될 때까지 유지되고 새 요청부터 새 설정이 적용된다. 재기동(restart)은 진행 중인 연결이 끊긴다
  • 주의systemd로 관리한다면 sudo systemctl reload nginx도 같은 동작이다
  • 연관먼저 "설정 문법 검사"를 통과시킨다

Prometheus / PromQL

삭제된 Pod의 재시작 횟수 확인

max_over_time(kube_pod_container_status_restarts_total{namespace="<namespace>", pod=~"<deployment>-[^-]+-[^-]+"}[7d])
  • 언제Pod가 이미 지워져 kubectl get pod로는 못 보는 재시작 이력을 사후에 확인할 때
  • 주의[7d] 같은 range vector가 핵심이다. 셀렉터만 쓰면 살아있는 Pod만 나온다 — kube-state-metrics가 삭제된 Pod의 시계열을 stale 처리하는데, staleness는 instant vector에만 적용되기 때문
  • 주의Grafana 시간 범위를 [7d]와 맞춰야 한다. Last 1 hour인 채로 [7d]를 써도 1시간 구간만 평가된다
  • 주의Grafana Explore 기준 Type Instant + Format Table. restartCount는 단조 증가라 최댓값이 곧 삭제 직전 최종 횟수다
  • 주의pod=~"<deployment>-.*"로 하면 이름이 겹치는 다른 Deployment까지 딸려온다. -[^-]+-[^-]+는 <deployment>-<RS해시>-<Pod해시> 형태에만 맞춘 패턴 (PromQL 정규식은 양끝이 자동 앵커링)
  • 연관kube-state-metrics v1.x는 레이블이 pod_name/container_name이다. 빈 결과면 레이블명부터 확인

재시작이 발생한 컨테이너만 추리기

max_over_time(kube_pod_container_status_restarts_total{namespace="<namespace>"}[7d]) > 0
  • 언제네임스페이스 전체에서 재시작을 겪은 컨테이너만 훑을 때
  • 주의PromQL의 비교 연산자는 기본이 필터다. 조건에 안 맞는 시계열은 결과에서 빠진다
  • 연관전수 확인은 > 0을 떼면 된다

컨테이너의 마지막 종료 사유 확인

max_over_time(kube_pod_container_status_last_terminated_reason{namespace="<namespace>", pod=~"<deployment>-[^-]+-[^-]+"}[7d]) > 0
  • 언제재시작이 OOM 때문인지 프로세스 에러인지 가를 때
  • 주의값은 항상 1이다. 재시작 횟수가 아니다. 정보는 reason 레이블(OOMKilled / Error / Completed)에 있다
  • 주의이름 그대로 마지막 종료 사유만 남는다. 여러 번 재시작하며 사유가 바뀌었다면 중간 이력은 안 보인다
  • 연관횟수는 kube_pod_container_status_restarts_total로 따로 본다

Pod 기동 시각 확인

max_over_time(kube_pod_start_time{namespace="<namespace>", pod="<pod>"}[7d])
  • 언제삭제된 Pod가 언제부터 떠 있었는지 알아야 할 때
  • 주의값이 Unix epoch(초)다. Grafana에서 Unit을 Time > Datetime (from seconds)로 바꾸거나 date -r <epoch> (리눅스는 date -d @<epoch>)로 변환
  • 연관Type Range + Format Time series로 그리면 값이 상수라 수평선이 된다. 선의 시작과 끝이 곧 Pod 생존 구간이라 epoch 변환 없이 X축에서 바로 읽힌다

Pod가 사라진 시각 확인

max_over_time(timestamp(kube_pod_info{namespace="<namespace>", pod="<pod>"})[7d:1m])
  • 언제Pod가 언제 삭제됐는지 역산할 때
  • 주의[7d:1m]은 subquery다. "지난 7일을 1분 간격으로 되짚으며 안쪽 표현식을 평가"한다는 뜻. timestamp()가 instant vector용이라 삭제된 Pod에 직접 못 쓰는 걸 이 형태로 우회한다
  • 주의결과는 메트릭이 마지막으로 수집된 시각이다. 정밀도는 스크랩 주기(보통 30s) 수준
  • 주의결과가 현재 시각과 거의 같으면 그 Pod는 아직 살아있는 것이다
  • 연관kube_pod_info는 값이 1인 info 메트릭. created_by_name 레이블로 소유 ReplicaSet을 확인할 수 있어 Pod 이름 패턴 검증에도 쓴다

skopeo (컨테이너 이미지 복사)

레지스트리 로그인

sudo skopeo login <registry> -u <user>
  • 언제레지스트리에 push하기 전에, 또는 push가 denied: requested access to the resource is denied / unauthorized: authentication required로 실패할 때
  • 주의<registry>는 포트까지 포함한 주소다 (예: registry.example.com:5000). 비밀번호를 물으면 레지스트리 쓰기 권한이 있는 토큰을 넣는다. GitLab이면 write_registry 권한이 있는 Personal Access Token이나 Deploy Token이다
  • 주의로그인 정보는 실행한 사용자별로 저장된다. push를 sudo로 할 거면 로그인도 sudo로 해야 한다. root는 /run/containers/0/auth.json에 저장되며, /run은 재부팅하면 지워진다
  • 주의로그인했는데도 denied만 나오면 계정 권한 문제다. GitLab은 그 프로젝트에 Developer 이상이어야 push할 수 있다

cri-o 노드에 있는 이미지를 레지스트리로 push

sudo skopeo copy "containers-storage:[<driver>@<root>+<runroot>]<image>:<tag>" docker://<registry>/<image>:<tag>
  • 언제cri-o(또는 podman) 노드에 받아져 있는 이미지를 레지스트리로 올릴 때. crictl에는 push 기능이 없다
  • 주의containers-storage:는 cri-o·podman이 쓰는 로컬 이미지 저장소에서 읽고, docker://는 레지스트리에 쓴다. 이미지 이름에 레지스트리 주소가 들어 있으면 앞뒤 이름이 같아도 된다
  • 주의[<driver>@<root>+<runroot>]는 저장소 위치 지정이다. cri-o가 기본 경로(/var/lib/containers/storage)를 쓰면 대괄호 부분을 통째로 빼도 된다. 다른 경로를 쓰면 넣어야 하고, 안 넣으면 이미지를 못 찾는다. 대괄호를 쉘이 해석하지 않도록 따옴표로 감싼다
  • 주의저장소가 root 소유라 sudo가 필요하다. cri-o가 실행 중이어도 읽기는 괜찮다
  • 주의ERRO Failed to parse the authentication scope는 다른 저장소에서 레이어를 가져다 쓰려다(cross-repo mount) 나오는 메시지로, 이후 작업은 계속 진행된다
  • 주의저장소에는 레이어가 압축 풀린 상태로 있어서 push할 때 다시 압축한다. 같은 이미지라도 manifest digest가 바뀔 수 있다
  • 연관<driver>, <root>, <runroot> 값은 [kubernetes](kubernetes.md#cri-o-이미지-저장소-경로-확인)에서 확인한다

SSH

제어 소켓으로 접속 재사용 (master 연결)

ssh -f -N -M -S /tmp/<name>.sock -o ControlPersist=1h <user>@<host> -p <port>
  • 언제비밀번호·OTP 인증을 한 번만 하고, 이후 여러 명령이나 스크립트가 같은 연결을 재사용하게 할 때
  • 주의SSH 연결 멀티플렉싱이다. 인증된 통로를 소켓 파일로 노출해 두고, 이후 접속은 이 소켓을 통해 인증 없이 붙는다
  • 주의-M = master 모드(소켓을 만드는 쪽), -S = 소켓 파일 경로, -f = 인증 후 백그라운드로 내려감, -N = 원격 명령 없이 연결만 유지, ControlPersist=1h = 마지막 사용 후 1시간 동안 유지
  • 주의소켓 파일 권한이 곧 접속 권한이다. 다른 사용자가 읽을 수 있는 경로에 두지 않는다
  • 연관상태 확인 ssh -S /tmp/<name>.sock -O check <user>@<host>, 종료 ssh -S /tmp/<name>.sock -O exit <user>@<host>

제어 소켓으로 원격 명령 실행

ssh -S /tmp/<name>.sock -p <port> <user>@<host> '<command>'
  • 언제master 연결이 떠 있는 상태에서 인증 없이 원격 명령을 실행할 때
  • 주의원격 명령은 작은따옴표로 감싸야 로컬 셸이 $변수나 |를 먼저 해석하지 않는다
  • 주의zsh에서는 S="ssh -S ..." 처럼 변수에 담아 $S '<command>'로 쓰면 변수 전체가 명령 이름 하나로 취급돼 no such file or directory가 난다. 그대로 적거나 함수·alias로 만든다
  • 주의원격 명령이 멈추면 로컬도 같이 멈춘다. 오래 걸릴 수 있는 명령은 원격에서 timeout <초>로 감싼다

떠 있는 제어 소켓과 접속 대상 매핑 확인

ps -ef | grep '[s]sh .*-S '
  • 언제/tmp에 소켓이 여러 개 있을 때 어느 소켓이 어느 서버로 연결된 것인지 볼 때
  • 주의[s]sh는 grep 자신이 결과에 걸리지 않게 하는 방법이다(정규식 [s]는 s 한 글자와 맞지만 grep 명령줄의 문자열 [s]sh와는 안 맞는다)
  • 주의소켓 이름만 보고 판단하지 말고, 붙은 뒤 첫 명령으로 hostname을 찍어 대상 서버가 맞는지 확인한다

systemd / journalctl

서비스 로그를 시간 범위로 잘라내기

journalctl -u <service> \
  --since '<since>' \
  --until '<until>' \
  --no-pager > out.log
  • 언제장애 발생 시각을 아는 상태에서 그 구간만 떼어내 분석할 때
  • 주의--no-pager를 빠뜨리면 파일로 리다이렉트할 때 페이저에 걸려 멈춘다
  • 주의시각 형식은 'YYYY-MM-DD HH:MM' (예: '2026-09-16 19:10'). 따옴표 필수
  • 연관상대 시간도 된다 — --since '30 min ago', --since yesterday

서비스 로그 실시간 확인

journalctl -u <service> -f
  • 언제조치를 넣고 반응을 바로 보고 싶을 때
  • 연관-n 100으로 최근 줄부터 시작 — journalctl -u <service> -n 100 -f

특정 우선순위 이상만 보기

journalctl -u <service> -p warning --since today --no-pager
  • 언제로그가 많아 WARNING/ERROR만 걸러내고 싶을 때
  • 주의-p는 지정 레벨 이상을 포함한다. warning이면 warning/err/crit/alert/emerg
